# Adversarial review of the Tenure platform architecture

An independent reviewer was asked to find only defects — contradictions between sections
(they were authored in parallel), SQL or RLS that would not hold, generic boilerplate
without implementable detail, and anything that would not survive contact with the
existing Tenure codebase. Nothing here was written by the section authors.

## P0 — the design does not work as written

**1. RLS bootstrap deadlock. The app cannot authenticate anyone.** (§6.2, "Executable PostgreSQL" → RLS enable loop)
`InstitutionMembership` is in the `ENABLE/FORCE ROW LEVEL SECURITY` array, and `tenancy.current_tenant()` *raises 42501* when the GUC is unset. But §6.2's own sequence diagram calls `getUserContext(userId)` **before** `withTenant` — it must, because reading memberships is how you validate the `/t/{slug}` segment. Same for `RoleAssignment` (needed for non-staff), `Organization` (slug→id), and `ConfigValue` layer 10 (`auth.devLoginEnabled` is needed at sign-in, before any tenant; the `platform_config_read` PERMISSIVE policy does not save you because the OR'd `tenant_isolation` branch raises). In the fail-empty variant it's worse, not better: zero memberships → `notFound()` for every user, silently. `src/lib/rbac.ts:24-55` and `src/lib/auth.ts:16` (`PrismaAdapter(db)`) both run outside any tenant scope today.
**Fix:** name a bootstrap primitive. Either `withActor()` that sets only `app.actor_id` plus self-row policies (`"userId" = current_setting('app.actor_id', true)`) on `InstitutionMembership`/`RoleAssignment`/`User`, or a `SECURITY DEFINER` function `auth.memberships_for(uuid)` granted to `tenure_app`. This is the load-bearing missing piece of the whole isolation design, not a detail.

**2. Two incompatible `withTenant`s, two GUCs, two failure semantics — both labelled "real code, not pseudocode."** (§6.3 Layer 3 vs. "The context primitive")
§6.3: `withTenant(scope, fn)`, GUC `app.institution_ids` (comma-joined list), policy `= ANY(app.current_institutions())`, **fails empty**, canary test asserts 0 rows (D3). Tenancy Isolation: `withTenant({tenantId, purpose}, fn)`, GUC `app.current_tenant_id` (scalar uuid), policy `= tenancy.current_tenant()`, **fails loud**, generated test asserts `rejects.toThrow(/42501/)` — and explicitly argues the first design is a bug ("Fail loud, not fail empty"). §6.3 exports the client from `src/platform/db/client.ts` behind ESLint; the other replaces `src/lib/db.ts`'s `db` with an AsyncLocalStorage Proxy that throws. P2, D3 and D4 all reason from the fail-empty version. **Fix:** delete one. Fail-loud is correct; then P2/D3/D4/§1.2's "converts silent reads into empty result sets" all have to be rewritten, because they currently sell the opposite property as the migration's core justification.

**3. The list GUC is not isolation for exactly the accounts G3 exists to protect.** (§6.3 Layer 2/3, R2, D3)
`readableInstitutionIds` = the user's memberships plus the institutions of their member orgs, joined into one GUC, used in both `USING` **and** `WITH CHECK`. For a two-institution staffer, every statement in the transaction can read *and write* both tenants. A forgotten `where` is then a cross-tenant write, and D1's detection story (fuzz suite asserting 404 per route) passes while the database layer is wide open. **Fix:** scalar tenant GUC for all writes, unconditionally. If cross-institution reads are genuinely needed for the ~8 surfaces in R2, add a separate `withCrossTenantRead(ids)` that sets a distinct GUC consumed only by `FOR SELECT` policies, enumerate its call sites, and audit every use.

**4. The effective-permission SQL grants full authority to suspended and disabled people.** ("Capability, entitlement, and the effective-permission rule")
The `grants` CTE filters `ra.state='CONFIRMED'` and effective dates and never touches `tenant_membership.state` or `principal.disabled_at`. The prose rule ("if and only if (a) assignment (b) scope (c) pack enabled") omits it too. So `SUSPENDED`/`LEFT` members and disabled principals keep every capability, forever. The `DenyReason` enum ships `MEMBERSHIP_SUSPENDED` with no code path that can produce it, and this contradicts D9's `User.disabledAt` mitigation. **Fix:** join `tenant_membership` with `state='ACTIVE'` and `principal.disabled_at IS NULL` inside `grants`, and make membership state condition (0) of the stated rule.

**5. Tier comparison is string equality — upgrading a tenant revokes its capabilities.** (packs, `enabled` CTE)
`(c.min_tier IS NULL OR i.tier = c.min_tier OR i.tier = 'enterprise')`. finance declares `budget|ledger|consolidation`; `finance.budget.read` has `minTier: "budget"`. A tenant installed at tier `ledger` matches none of the three disjuncts for any budget-tier capability → the budgets UI 404s the moment you sell the upgrade. `'enterprise'` is not a tier any pack in the document declares. This falsifies the headline claim that "re-upgrading restores exactly the prior grants." **Fix:** ordered tiers (`tier_rank(pack_id, key)`), predicate `tier_rank(i.tier) >= tier_rank(c.min_tier)`, and a boot-time assertion that every `minTier` names a tier its own pack declares.

**6. §6.3's Layer-1 SQL does not execute.** `CREATE UNIQUE INDEX "Role_institutionId_positionCode_key" ON "Role" ("institutionId","positionCode")` → `column "institutionId" does not exist`. `Role` (`prisma/schema.prisma:188-214`) carries only `organizationId`. The Executable-Postgres section gets this right (ADD COLUMN, backfill from Organization, SET NOT NULL); §6.3 — the block a reader will copy — does not. **Fix:** add the column/backfill/NOT NULL before every index swap in §6.3, and reconcile the partial-index inconsistency (`positionCode` is nullable; one section uses a partial index, the other doesn't).

**7. G2 is undercounted, and the missing one is the dangerous one.** `ApprovalRequest.idempotencyKey String? @unique` (`schema.prisma:391`) is a fifth global unique. §1.1, G2 and §5.3 risk #3 all say "four"; only the Executable section finds it. This is not a charter-blocking collision — it is a client-supplied key whose collision makes tenant B's retry resolve to tenant A's approval. **Fix:** fold into G2 and reclassify as a leak.

**8. Three mutually exclusive target schemas, all marked MVP.** §3.1 says rename `Role`→`Seat` with `@@map("Role")`, keep everything. "Domain & hierarchy model" replaces `Organization`→`org_unit`, `Role`→`position`, `RoleAssignment`→`role_assignment` (keyed on `principal_id`), `DirectoryPerson`→`person`, `User`→`principal`+`app_user`+`identity`, snake_case, uuid, composite `(tenant_id, id)` PKs — and puts all of it under "Build now". Tenancy Isolation says "**We do not rename `Organization` to `OrgUnit`**"; Executable Postgres says "**Do not rename.**" The hierarchy section also silently repudiates **D2** ("keep `institutionId`, do not rewrite 384 sites") and **D6** ("keep cuid; a PK migration buys nothing and risks everything") — it migrates every PK, every FK, every table name and all 383 sites. **Fix:** delete two. Only the sidecar-`OrgUnit` version is consistent with §1.3's gate timeline and R8's economics.

**9. `AuditEventPart` invents columns the codebase does not have and drops required ones.** Real `AuditEvent` (`schema.prisma:868-886`) is `(id, institutionId, actorId, actorRole, action, resourceType, resourceId, organizationId, outcome, reason, metadata, traceId, occurredAt)`, `outcome` NOT NULL with no default. The partition DDL declares `actorUserId, decision, entityType, entityId`; the config-publish transaction then does `INSERT INTO "AuditEventPart" ("tenantId","actorUserId","action","decision","entityType","entityId","metadata")` — five of seven columns don't exist and the NOT NULL `outcome` is never supplied. Every existing writer (`src/lib/admin/guard.ts:63-78`, `approvals/actions.ts`) uses the real shape. **Fix:** write the DDL against the actual model.

**10. RLS is never enabled on the partitions.** Policies on a partitioned parent apply through the parent; a query against `"AuditEvent_2026_08"` directly — retention job, support console, analytics, `\copy` — is unfiltered. The monthly partition-creation job must ENABLE/FORCE + attach the policy. Separately, **none** of the new authorization tables ever appear in any RLS list: `org_unit*`, `role_template*`, `position`, `role_assignment`, `tenant_pack_installation`, `policy`, `calendar_period`, `person`, `attribute_definition`. The tables that decide who can do what are the ones with no isolation specified.

**11. Columns and tables that are FK'd, GRANTed, or REVOKEd but never created.** `LedgerEntry_legalEntity_fkey` references `LedgerEntry."legalEntityId"` — `LedgerEntry` (`schema.prisma:745-770`) has no such column and no migration adds it (nor to `Budget`/`BudgetLine`/`Transaction`/`Vendor`, where rule 2 says it's NOT NULL). `"FieldDefinition"` and `"SecureFieldValue"` appear in the RLS loop and the support GRANT block and are defined nowhere. `"TenantPlacement"` is REVOKEd and never created.

## P1 — will not survive contact with the codebase or the platform

**12. The database roles cannot be created, cannot log in, and cannot migrate.** `tenure_migrator` is not `tenure_owner` and does not own the tables → `must be owner of table "Organization"` on the first ALTER; nothing grants ownership. `CREATE ROLE tenure_app LOGIN … PASSWORD NULL; -- IAM auth` — no `GRANT rds_iam`, `iam_database_authentication_enabled` is not set in `rds.tf`, and Prisma has no credential-refresh hook for 15-minute IAM tokens on a long-lived pool. Most importantly: **today the container composes `DATABASE_URL` from the RDS master secret** (`scripts/entrypoint.sh:7-18`), i.e. the app runs as the table owner. No section describes that cutover, which is a prerequisite for every claim in the RLS section.

**13. "Two Prisma clients, two datasources, one database" (§6.1) is not something Prisma does.** One `datasource` per schema. Two clients = two schema files, two generated clients, two pools — and no `$transaction` spanning `control` and `public`, which D13 explicitly requires ("idempotent, transactional"). It also doubles connections on `db.t3.micro` at the exact moment the doc argues connection budget is binding, and `resolveActorScope` adds a control-plane round trip to every request. Meanwhile §6.4's `@@schema("control")` requires the `multiSchema` preview feature, which the document never enables and which the placement table dismisses in another context. **Fix:** one datasource, `multiSchema` on, `control` as a schema in the same Prisma schema, isolation by GRANT — or state that provisioning is two-phase with a reconciler and drop "transactional".

**14. Redis is both "do not build at MVP" and a hard dependency of the authorization path.** D19 and §6.5 say unused at MVP; §6.5's own risk column says "a cache bug is a cross-tenant leak with no DB backstop… this is why the cache is deferred". The Domain section then puts the authorization decision in it (`authz:{tenantId}:{principalId}:{authzVersion}`, 60s TTL). And the invalidation doesn't work: `authz_version` lives on `tenant_membership` (per principal), so a `role_template_capability` edit or a `tenant_pack_installation` downgrade must bump *every affected membership row* in the same transaction — an unbounded fan-out UPDATE triggered by a billing event, never specified. So "downgrading removes `finance.ledger.post` from every actor on the next request" is false.

**15. The session carries a membership list — that is an authorization claim.** P4, D9 and the rejected-alternatives list all insist tokens carry no authority. The Domain section: the session carries "a list of `tenantId`s the principal is a member of." Grant a membership and the user can't reach the tenant until re-login; revoke one and anything that trusts the list to skip a check is stale. `Tenant.membershipEpoch` is a per-*tenant* counter (any change invalidates everyone's session there), is never written into the token, and is never compared anywhere. **Fix:** `sub` only. `getUserContext` (`src/lib/rbac.ts:24`) is already `React.cache()`d and already loads all memberships.

**16. Missing failure modes that will bite in week one.**
- **`redirect()` inside `withTenant`.** Server actions in this codebase end with `redirect(...)` (`src/app/(app)/approvals/actions.ts`), which throws a Next.js control-flow error. Inside `db.$transaction` that aborts the transaction and silently rolls back writes. Nothing in the doc says `redirect`/`revalidatePath` must live outside the scope body.
- **`React.cache()` is per-request, not per-scope.** Cached loaders memoize across `withTenant` blocks in one request. State the invariant that no `cache()`d function may return tenant rows.
- **No backfill reconciliation.** P1's "migration fails if backfill is inconsistent" is the symptom, not a plan. `Document`/`Event`/`Budget`/`Vendor`.`institutionId` are bare strings today with nothing enforcing agreement with the parent org; the FK will abort mid-migration. Specify a pre-flight mismatch count per table against a production snapshot in CI, and a resolution rule (parent wins), before any FK is added.
- **`ON UPDATE CASCADE`.** I ran `prisma migrate diff` on the composite-FK shape: Prisma emits `ON DELETE RESTRICT ON UPDATE CASCADE`. So `UPDATE "Organization" SET "institutionId"` rewrites the tenant of every child row — the exact drift P1 claims the FK prevents. Force `ON UPDATE RESTRICT`.
- **`suspended_tenant_readonly` is `FOR INSERT` only.** The doc's single worked RESTRICTIVE policy lets a suspended tenant UPDATE and DELETE freely.
- **No `prisma migrate` baselining plan.** `prisma/` contains only `schema.prisma` — there is no migration history, and production was built by `db push`. D12 gives this four words in a tradeoff column. It is the highest-risk step in G1 and needs `migrate diff --from-url`, a `--applied` baseline, and a verified no-op first deploy.
- **Per-tenant restore.** D1 accepts "no per-tenant PITR" and §6.7 defers `backup_retention_period` 1→7 to "the day a paying customer signs". Under pooled RLS, restoring one tenant is a side-instance restore plus filtered copy-back. That belongs in §1.3 as a gate with a runbook, not in a comparison table.

**17. Prisma composite-relation "caveat" is unnecessary FUD, and the fallback is worse than the problem.** I validated the exact shape on the pinned Prisma (6.19.3): a model with both `institution @relation(fields:[institutionId])` and `organization @relation(fields:[organizationId, institutionId], references:[id, institutionId])` validates and emits the composite FK correctly. Delete the caveat; do not "drop the direct institution relation on child models", which would break `Institution`'s relation lists and every `include: { institution: … }`.

## P2 — boilerplate with nothing implementable behind it

**18.** **P8's "display/title layer"** — no table, no key, no resolution order, no migration for the 5+ files containing `"Ainslie OSE"`. §6.4 says it becomes `Institution.staffOfficeName`; the `branding` kernel says "terminology overrides / terminology map only". Three answers, zero schemas. **P12's "the same wrapper covers club-side server actions (14 files)"** — `requireCapability` takes a `CapabilityId` from a 16-entry admin table; there is no capability id for any club-side predicate (`canManageRoster`, `canEditOrg`, `canManageFinance`). "Extend it" is an entire design. **`attribute_definition`'s Zod cache "invalidated by `authz_version`-style stamp"** — `authz_version` is per-membership; there is no tenant-level stamp; "-style" carries the sentence. **`retention.onDisable: "RETAIN_READONLY" // the only legal value`** — a single-valued enum is a comment; nothing makes a disabled pack's tables read-only, and the one RESTRICTIVE-policy example is never generalized. **Boot-time validation "refuses to boot"** in a Next.js/ECS app where "boot" is ambiguous, and its own rule #2 ("capability keys namespaced with the pack id prefix") is violated by every capability in the doc's finance manifest (`finance.budget.read` vs pack id `pack.finance`). **`restrictiveMeet(def, value, r.value)`** = "AND / min / intersect" with no rule for deriving which from `valueSchema`.

**19. Tenant-editable regex still ships, and it grants privilege.** `finance.roleNamePatterns` replaces `rbac.ts`'s finance regex with a tenant-writable config key — i.e. a customer admin edits a value that decides `canManageFinance`, classified `sensitivity: "standard"` with no `requiresCapability`. The guard pattern `^[^(*+?{]*(\|[^(*+?{]*)*$` does not exclude `[a-z]`, `.`, `\b`, `^`, `$`, or backreferences, and is itself run against attacker-controlled input. The doc names the right answer ("do not accept regex at all… take a list of case-insensitive substrings") and then ships the regex anyway. Take the substring option and set `requiresCapability: "institution.grantRole"`.

**20. Scope/timeline incoherence.** §1.3 gates the work at ~6 sprints (G1–G6). §1.4 says explicitly: not a policy engine, not a rules DSL, not a workflow engine, not a JSON-configured behaviour system. The later sections then specify a versioned `policy` engine with schema registry and upgrade functions, a `workflow_definition/instance/step` kernel with suspension semantics, a pack manifest system with 12 declaration arrays and boot-time validation, an identity rewrite (`principal`/`identity`/`tenant_membership`), an effective-dated org graph with closure tables and PL/pgSQL triggers, and a seven-layer configuration engine with draft/publish/rollback/effective-dating/JSON-Schema/two-tier cache/LISTEN-NOTIFY — all in "Build now (multi-tenant correctness is not optional and does not phase)". None of that is required for tenant #2. **Fix:** make §1.3's gates the spec, move everything from "Domain & hierarchy model" onward into a clearly-labelled Phase 4+ appendix, and delete its claims of MVP status. As written a reader cannot tell which document they are supposed to build.

**21. 404-vs-deny-reason contradiction.** §6.4 `requireModule`: "404, not 403 — do not disclose the SKU." Packs section: "`SUSPENDED` must be distinguishable from `DISABLED` in the deny reason… Collapsing them into a generic 404 produces support tickets that take a week to resolve." Same check, opposite rules. Resolve: 404 for non-members; structured reason for authenticated members of the tenant.

**22. Citation drift (fix before publishing).** Most citations land exactly. Two do not: `approvalDelegation.deleteMany({})` is `scripts/seed.mjs:341`, not `:325`; the counts are **383 occurrences across 61 files**, not "384 across ~61". Also `app.current_institutions()` is created in a schema `app` that no DDL creates. This document's authority rests on precise citation — a reviewer who finds one that doesn't land discounts all of them.
